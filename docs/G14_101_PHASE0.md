# G14 Phase 0 (claim-096): the 101's divergence list

**Status: measured, host-side, 2026-08-26.** Instrument
`sim/sim.cpp --g14`, one command, no hardware, no lease. Artifact: the tool's
own output, reproducible with `cd sim && make && ./superos101-sim --g14`.

    subject  src/engine.h, native, compiled for the host
    oracle   the genuine 80C49 mask ROM under src/emu101.cpp, same binary
    driver   identical input to both, stepped by VIRTUAL TIME
    compare  observable outputs only

## The number

    matched 6   diverged 14   UNTESTED 0   of 20 behaviours
    by stream:  cv 7   gate 6   order 14   vco 0

**The 14 divergences are FOUR root causes, not fourteen.** Counting rows
rather than causes is how a divergence list becomes a to-do list nobody can
act on. Per CLEANROOM.md the untested count is published next to the matched
one: it is 0 here, meaning every listed behaviour produced an observable
change in at least one subject. That is not a claim that the behaviour SET is
complete: see "what this does not cover".

## The four divergences

**D1 -- CV and gate move in the same instant; the original writes CV first.**
Channel: time (audible, so also sound once that channel has a tolerance).
14 of 20 behaviours, i.e. every behaviour that opens a gate at all.
`engine.h` returns `Output{cv, gate}` from one `update()` and `main.cpp`
writes both in one pass, so the observable surface changes once. The ROM
writes the new CV-OUT value to the S/H and raises the gate on a LATER pass:

    engine  17/G 17/.
    ROM     17/. 17/G 17/.

This is the only divergence in behaviours 1, 2, 4, 16, 18, 19 and 20, so it
is worth closing first: it alone would move matched from 6 to 12.

**D2 -- note priority: the original takes the lowest held key, `engine.h`
keeps the key it already had.** Channel: state. Behaviour 3.
Hold key 10, then also press key 0 (lower), then release key 0:

    engine  27              (never moves)
    ROM     27 17 27        (takes the lower key, gives it back)

`engine::NoteEngine::pickKey` (`src/engine.h:295`) has three arms, and the
middle one keeps `heldKey_` whenever it is still in the mask. So with
`lastNotePriority` false the engine implements *first*-note priority, not the
lowest-note priority the machine is documented to have. This is the one
divergence here that is a plain defect rather than a modelling choice.

**D3 -- the original does NOT retrigger the gate between arpeggiator steps.**
Channel: state and time. Behaviours 10-15.
Eight arp steps under an external clock:

    engine  gate rises 8 times, once per step
    ROM     gate rises ONCE and stays high for the whole run

**Attributed, not assumed.** `emu101.cpp`'s gate shaping deliberately holds
the pin high across arp steps (`RomRetriggerCertain()` requires the ROM's
PLAY bit, which arp mode does not set), so the physical pin alone could not
tell the ROM's behaviour from our own firmware's. `emu101::romP2()` was added
to publish the gate bit **the ROM itself wrote, before shaping**, and the
harness prints both with an explicit attribution line. The raw ROM gate rises
once too, so this is the original's behaviour and not our shaping layer.

**Robust to the clock duty cycle**, which was the obvious alternative
explanation: driven at 8 %, 50 % and 92 % duty, the ROM holds the gate in all
three (behaviours 10, 14, 15).

**D4 -- the arpeggiator's first step gates the PREVIOUS pitch.** Channel:
time. Behaviours 10-15, visible as the leading value in the ROM's cv stream
(`29 17 21 24 ...` against the engine's `17 21 24 ...`). The ROM opens the
gate on whatever the S/H was holding and moves to the first key on the next
clock; `engine.h` steps first and gates the first key. One step of phase.

## What MATCHES

Behaviours 5-9 and 17, exactly, on all four streams:

* OCTAVE up and OCTAVE down
* RANGE 16', 4' and 2' (the VCO-range S/H stream is byte-identical, and the
  `vco` column is 0 divergences across all 20 behaviours)
* HOLD button latching a key

## The red condition, which is what makes the above worth reading

An empty or small divergence list from a comparator that has never produced a
divergence on a deliberately broken subject is the claim-081 failure mode
wearing a green hat. `G14_BREAK` damages the SUBJECT at the observation point
and the comparator must go red:

    break            matched  cv  gate  order  vco
    0 (none)              6    7     6     14    0
    1 pitch off by one    0   20    17     20    0
    2 gate inverted       0    7     7     20    0
    3 wrong VCO range     0    7     6     14   20

**Each break moves its own stream and only its own stream.** Break 3 takes
`vco` from 0 to 20 and leaves `cv`, `gate` and `order` at their clean values,
which is the evidence that the streams are independent and that the
comparator localises rather than just alarming.

## What this does NOT cover, stated so it is not read as coverage

* **The sound channel has no pass condition** (CLEANROOM.md). Edge placement
  in microseconds is recorded and printed and is **not scored**. D1 and D3
  are audible and will need it; nothing here picks a tolerance.
* **The behaviour set is 20 items chosen by me and is not exhaustive.**
  UNTESTED is 0 with respect to that list, not with respect to the machine.
  Not exercised at all: KEY TRANSPOSE as a pitch function, portamento, the
  RANDOM S/H route, pattern lengths past 3 steps, the LFO as clock source,
  the pedal and HOLD interacting with the sequencer.
* **State-channel readback is not byte-compared.** The ROM keeps its pattern
  in 80C49 RAM and `engine.h` in its own step bytes; the two encodings are
  compared only through what they play. A byte comparison needs a stated
  mapping and is Phase 1 work.
* **Everything host-side.** No hardware ran. The oracle is the mask ROM under
  our emulator, so anything our emulator gets wrong, this inherits.

## Extensions, excluded on purpose rather than forgotten

Not divergences: the original never had them, so they are outside 1:1 by
construction. SysEx (0x10..0x4D); 8 flash-backed patterns of up to 128 steps
against the ROM's one battery-RAM pattern; the MIDI clock divider table; live
host edits under clock; USB-MIDI, the 0x3B probe and the 0x3E bench window.

## Does HLE change what the oracle should be

**No.** `emu101_hle.h` executes the ROM's key-scan loop natively but is
required to be instruction-exact: same registers, same carry, same F1, same
exit PC, same cycle count, and it is enabled only when the ROM bytes match
`HLE_SIG`. It is a speed path, not a behaviour path, so it cannot move an
observable output. The oracle stays "the mask ROM under emu101". If HLE ever
grows a fast path that is only *behaviourally* equivalent, that stops being
true and this answer has to be revisited.

## Next

D2 is a defect and is closeable now. D1 is a one-line ordering change in
`main.cpp` with a real risk attached (see `8c0a865`: every signal moved has to
stop being observable in its old form at the same instant). D3 and D4 are
behavioural questions that want a hardware capture before anyone changes
`engine.h` to match, because matching them makes the arpeggiator sound
different.
